# GPU 执行链主线化计划

本计划规定下一轮架构整合的交付范围，供实现与独立审阅使用。它描述目标结构，当前实现仍以[设计书](../architecture/system-overview.md)为准；进度统一登记于[当前实施计划](solver-consolidation-plan.md)，运行证据统一登记于[验证指南](../maintenance/validation.md)。

执行顺序：完成本文 G1—G6，再进入[仿真能力补全计划](simulation-capability-completion-plan.md)。本文交付期间保持现有物理模型；仅为迁移所必需的状态交接与执行组织调整进入本轮。

## 1. 已确定的决策与本轮完成范围

- Vulkan 常驻求解成为唯一生产物理实现，删除 CPU 完整求解和 CPU＋GPU 压力混合路径。
- 后续新物理功能直接实现于 GPU。宿主保留世界交互、定义加载、数据编码、事务协调、设备管理和按需观测。
- 初始化、编辑、恢复在宿主处理有限库存和数据结构；连续时间演化统一调用 GPU。G3 暂留现有编辑专用的静态拓扑、排水和动量／能量交接，退出时点为 S2 生产替换交付。
- 不保留完整 CPU 仿真作为测试参照或故障接管。无可用设备时，仿真区域保持不可推进状态，存档及世界操作由生命周期规则处理。
- 保留已有整数物质、物种和体积余量的表示及其有效算法。本轮不同时改气体模型、求解精度、空间分辨率或库存量化。
- 交付包括源码、调用方、构建与测试入口、运行配置、文档和旧路径删除。仅将默认配置设为 GPU 不构成交付。

当前[后端参考](performance-and-backends.md)中的“CPU 作为参考与恢复后端”、切换后端及旧 probe 说明，与本轮目标存在冲突；实施时以本文用户决策为准，并在 G6 同步更新。只读[GPU 备忘录](../architecture/gpu-execution-principles.md)保持原样。

## 3. 目标数据归属和模块分工

### 3.1 状态种类

| 对象 | 保存内容 | 生命周期及写入者 |
|---|---|---|
| 世界定义 | 材料、物种、热参数、反应、单位与注册 ID | 宿主加载，设备取得只读表 |
| 已提交运行状态 | 各相库存、组成、内能、MAC 动量、实体和相变续算数据 | GPU 持有当前代；应用层采用完整后继 |
| 待提交候选 | 机械、热学或编辑操作的完整后继 | 时间步由 GPU 生成；G3 编辑由宿主规划并写入设备私有候选；统一采用或释放 |
| 宿主快照 | 同一代的可序列化权威状态 | 显式 checkpoint／编辑导出产生；无自主步进能力 |
| 几何与派生缓存 | 固定碰撞、相占据派生、索引、物性、求解工作区 | 按来源代次复用；不单独决定物质数量 |
| 外部输入 | 方块几何变化、物品转移、实体目标、热与机械外源 | 宿主按请求收集；只在成功提交后落实外部效果 |

宿主快照与设备内存可以为同一代同时存在；代次采用后，旧快照只作为旧代捕获。删除“读取 `domain()` 顺便更换当前状态所有者”的行为。

状态解码不得构造带完整机械／热化学阶段的 CPU 域。量值编码、有限库存加减、定义检查、碰撞采样和纯几何导出可以继续使用 Java。

### 3.2 模块安排

优先保留现有 Gradle 模块，减少同时修改构建拓扑的工作量：

- `model` 持有可保存状态、量值规则和物性定义。
- `solver` 收敛为求解请求、候选与观测契约，以及仍被宿主使用的几何／状态操作；删除 CPU 时间演化。若某文件已成为纯模型，移至 `model`，避免 GPU 依赖旧求解域。
- `gpu-kernel` 持有唯一数值演化、设备资源与阶段调度。
- `app` 维持区域操作、调度与提交协调，通过求解契约访问设备。
- `fabric` 完成世界采集、物品与 WAL、存档、命令、客户端快照。

保留接口的理由仅限模块依赖和资源生命周期。删除为多种生产后端切换设置的分支。现有 ServiceLoader 可作为单一实现的模块装配机制保留，无须为移除 CPU 再造注册框架。

`mmm.gpuprobe` 中生产代码与验证入口需明确分开。包名迁移随 G4 整理一次完成，保留资源路径与 shader 标识的稳定性，避免将包名、物理模型和资源 ID 同时重写。具体类名由实现确定，本文按职责划分。

## 4. 目标执行与交接

### 4.1 普通步和独立热轴

1. 宿主捕获已提交代与本次输入，申请设备候选。
2. 设备依次完成同代几何／物性准备、力与约束、接受通量、库存与动量及功结算、热化学和后继状态。
3. 设备产生所需统计和提交结果；常规观察只回读需要的摘要或展示数据。
4. 应用层核对区域身份、输入代与生命周期，采用完整后继，再一次应用世界／实体副作用。
5. 失败候选释放；设备仍可用时原已提交代继续有效。不得为生成统计而恢复 CPU 域。

独立热轴沿同一候选与提交协议，保留当前相变待机械同步职责。第一份计划不更改热力分裂算法。

### 4.2 初始化与冷恢复

初始化器直接构造状态载荷和固定几何；GPU 导入后完成需要的物理派生准备。演示、控制器、采样和接管复用同一入口。

冷恢复顺序为世界定义与 WAL/HEAD 分类 → 同代完整库存解码 → 世界区块与碰撞准备 → GPU 导入 → 生命周期恢复。加载过程中允许读取已保存摘要。禁止通过 CPU 推进来“修复”恢复状态。

### 4.3 世界编辑与容器事务

本轮采用宿主编辑规划、设备候选发布的两层结构。当前 `MaterialTransferPlanner` 依赖邻格搜索、`CapacityRouting`、`prepareExternalMomentum` 和绝热气腔重映射；碰撞编辑还处理微盒支持拆分、颗粒重安置与受阻拒绝。现有 GPU 时间推进内核以面通量和相变状态为输入，G3 按现有编辑职责复用 Java 算法，避免为短期集总气腔专门新增一套设备编辑算法。

宿主编辑规划器接收明确代次的 `FluidDomainState` 快照及编辑请求，在私有数据上准备接受量、后继库存、几何、动量和热账。保留邻格搜索、`SignedDyadic` 分份、颗粒重安置，以及 S2 前所需的 `GasTopologyCoordinator`、`prepareExternalMomentum` 编辑职责。迁移时最小化调整这些类的数据依赖，切断 `DomainStep`、机械／热化学时间推进和后端选择；规划器接口只接收状态和操作，不暴露时间推进能力。

编辑结果通过 staging 写入现有 `VulkanLiquidRegion` 的私有候选槽，统一更新派生失效和代次，再沿应用事务采用。接受量、物品载荷、外部收支和后继状态来自同一份规划结果。设备将宿主已结算的编辑后继作为起点，后续普通步继续推进；编辑的动量修正与气腔功只执行一次。

- 组成及内能编辑：宿主规划有限库存变化与实际能量，再发布设备候选。
- 几何／容量编辑：宿主完成可达空间搜索、支持拆分、排水、颗粒安置和当前气腔交接；预览返回完整接受结果或具体受阻原因。
- 注入／提取：宿主计算实际接受量并协调物品与 WAL，候选发布复用同一结果。
- 清空、排气、移除、接管／归还：复用现有事务恢复分类。

同尺寸且当前容量足够的编辑复用布局与设备资源。快照读取保持当前设备代有效；候选支持完整状态写入和已确认影响范围的增量写入，避免每次操作重新构造 `VulkanLiquidRegion`。跨区域的气腔变化可能要求全域读取／重算，性能记录同时计入回读、规划和写入。布局容量不足时沿现有扩容职责处理。`importRoundoff` 记录槽位整理前后能量表示之差；稳定状态往返的幂等性与实际编辑能量结算分别检查。

G3 明确保留一段编辑专用的 Java 物理交接，G5 删除范围据此列出例外。G4 对其及现有气腔／Schur 内核只做必要依赖解耦。S2 交付时迁移编辑、恢复与普通推进对局部气体的共同处理，再删除这段集总气腔静态交接；若 S2 尚未完成，例外仍是显式未结事项。局部气体仍需要容量、密封压缩、受阻排水、颗粒安置和质量改变后的动量结算，S2 应逐项承接这些职责。编辑请求、事务回执、候选发布及资源复用接口继续沿用。

### 4.4 保存、卸载和设备故障

正常保存捕获一个明确代次，完整导出该代的物质、动量、内能及待处理状态，沿现有持久化协议提交。保存快照必须与 HEAD/WAL 的世界副作用相容。

区分两种失败：

- 普通候选失败：设备仍有效，保留当前代，报告实际阶段和原因。
- 设备丢失：停止访问失效设备状态，暂停所有受影响区域；从已有可恢复 checkpoint 与日志重新建立状态，设备重新可用后才推进。

所有改变外部物品、持久方块状态、跨区域库存或外部设备内能的操作，必须在现有 WAL／分阶段提交协议中同时建立可恢复的区域后继数据，并以 HEAD 和日志决定唯一事务结果。外部效果不能先成为不可恢复的既成事实。这里要求可恢复的共同提交，不假定 Minecraft 世界、物品和区域文件具有一个底层原子写操作。

设备丢失后先处理未完成 WAL：检查已发布 HEAD、准备好的后继快照与外部成员，完成或撤销相应事务，再从一致的已持久代恢复。没有未决外部事务时，允许恢复最近有效 HEAD；其后的纯内部流动进度可能丢失，不必因此永久封锁区域。普通实体冲量、灭火等游戏响应不回滚也不重放，接受它们与回退流场之间的恢复误差；未来若把实体纳入精确能量系统，必须重新设计该契约。HEAD 损坏、事务成员不明确或设备仍不可用时保留具体暂停原因，不能“无条件回退”。

本轮不新增每步全量镜像，也不承诺自动重建显卡上下文。保留受控重新加载的恢复路径，设备重建策略按实际资源管理实现决定。

## 5. 分阶段交付

### G1：抽离状态与公共契约

改动：

1. 将 `FluidDomain` 内被请求、统计、查询、热端口和存档使用的公共类型移至其职责所在的独立类型；同类结果集中保存，避免每个 record 单独建文件。
2. 将 GPU 使用的时间细分预算等配置从 `CpuFluidSolverBackend` 迁出。
3. 拆开可保存状态、宿主编辑所需库存与 CPU 阶段处理器；明确哪些纯库存／几何算法仍需要保留。
4. 迁移 `VulkanFluidStateCodec` 的输入，使其无须调用完整 CPU 域进行导入准备。

完成条件：GPU 后端、状态 codec 和候选公共签名不再依赖 `FluidDomain` 内部类型或 `CpuFluidSolverBackend`；新建和导出／导入可直接使用状态载荷。临时适配仅服务尚未迁移调用者，在 G3/G5 删除。

### G2：统一运行态、候选及查询

改动：

1. `FluidRegion` 当前运行态收敛为设备常驻状态；未加载状态保留明确的宿主快照和生命周期。
2. 将机械、热学候选的 CPU／GPU 分叉收敛为设备候选；删除 `claimPreparedCpuDomain` 及对应采用分支。
3. 查询、液位、热设备摘要、实体接触、展示均通过已有常驻观测接口或专用小批读取。
4. 保留请求代次、候选单次采用、失败释放和实体响应只发布一次的约束。

5. 单列迁移 `prepareGroupAvailability` 和 `replaceThermalBoundaryTemperatures`：前者当前会调用 `domain()` 导出并关闭常驻状态，后者也隐式恢复宿主域。活动组需要同代气体、实体和热接触连通关系，不能仅用固定墙邻接替代；由设备提供精简分组摘要，宿主传播区块可用性，或直接在设备维护分组。可用性变化只更新输入与活动掩码，热参数变化只提交候选。

完成条件：正常连续推进、暂停单步、显示和普通查询不恢复 CPU 域；观察不会切换状态所有者；统计与资源释放不需要完整回读。

### G3：迁移初始化、编辑、持久化完整链

逐条迁移以下入口，避免只迁移演示路径：

| 业务 | 源码定位 | 必须接通的后继流程 |
|---|---|---|
| 新建、配方和演示重置 | `FluidRegionFactory`、`MinecraftDebugFixtures`、`DemoTankOperations` | 构造状态 → GPU 准备 → 暂停或推进 |
| 世界碰撞变化 | `FluidRegionWorldInteraction`、`DomainCollision`、`LiquidCollisionEdit` | 几何候选 → 接受容量与库存 → GPU 继续 |
| 桶、发射器和外部接口 | `MinecraftContainerTransactionAdapter`、`FabricTransferApi` | 接受量 → WAL/物品 → 同代库存 → 恢复后续算 |
| 灌溉与气源 | `FarmlandMoistureOperations`、相关气体操作调用方 | 有限源汇 → 实际接受量 → 世界效果 |
| 有限热设备 | `FluidRegion` 热端口与设备操作 | 装卸载荷、内能、候选及接触数据 |
| 清空、排气、释放和移除 | `MinecraftRegionLifecycle` | 预览、取消、持久提交、失败后重试 |
| 采样／接管／归还 | `OwnershipTransactionCoordinator` | 世界库存与区域库存及日志一致 |
| 保存／冷恢复／卸载 | `MinecraftRegionCheckpointSource`、`RegionCheckpointRestorer` | 同代快照 → HEAD/WAL → GPU 恢复 |

涉及的调用方位于 [Fabric 仿真目录](../../fabric/src/main/java/mmm/simulation/)；存盘协议见[区域 checkpoint](../architecture/region-state.md)和[事务参考](../architecture/world-ownership-and-containers.md)。

完成条件：上述链路不再需要具有时间推进能力的 CPU 对象；编辑后可以继续 GPU 推进；恢复保留相变待位移、颗粒、气体和设备内能。设备失败时不能重复发放物品或丢失已提交外部库存。

有限热设备明确沿唯一 GPU 热步交换内能。删除 `FiniteHeatExchangerOperations.tickExchange` 中只对非驻留区域执行的 CPU 换热，以及 `FluidRegion.commitFiniteThermalExchange/commitFiniteThermalPortExchange` 的 CPU 专属推进；安装、拆卸改用设备库存快照与既有有限设备 WAL。查询和装卸不能为读取热状态而调用 `domain()`。

### G4：整理设备执行职责与布局

在现有 GPU 链上完成以下整理，不改变物理方程：

- `VulkanLiquidRegion` 保留区域状态、候选资源和高层步骤组织；工作区布局／容量、具体阶段录制按独立数据归属归并。
- 物理阶段可直接读出输入、输出、依赖与顺序；资源屏障按实际读写依赖集中安排，保留必要的阶段计时。
- Java 与 shader 的字段编号、header 偏移和布局约定采用单一声明来源。优先小型布局定义／生成常量或公共 include，不建立通用计算图语言。
- shader 展开压缩函数，使用带物理含义的变量，标明单位、读写字段和离散更新；普通公式修改无需穿透设备资源管理。
- 核查正常步全量复制、重复建表、额外提交与回读，只删除经调用关系确认冗余的工作；大规模求解器优化留在独立物理／性能交付。
- 明确生产入口与 headless 验证入口的源码位置和打包范围，保留同一生产内核供两者调用。

完成条件：区域类满足现有规模规则；一份布局声明能定位两侧字段；新增局部物性／源项可沿既有阶段加入；无平行“新调度器＋旧调度器”常驻路径。

### G5：删除 CPU 时间演化和混合路径

删除清单按实际引用最终确定，以下职责必须消失：

- `CpuFluidSolverBackend` 及其 CPU 候选恢复、时间推进和设备故障后接管。
- `DomainStep`、`MechanicalStepPipeline`、`ThermochemistryPipeline` 及只被 CPU 推进调用的压力、黏性、输运、热化学阶段。
- `ComputeExecution`、CPU 压力计算接入、混合 provider 和仅为混合后端服务的数量计算装配。
- `FluidDomain` 聚合求解器。仍有用的库存事务与几何算法必须已有独立去向；G3 编辑专用静态交接保留到 S2，集中登记其依赖和调用者。
- CPU 运行选项、后端切换、双态候选、CPU 参照完整步测试及只服务已删除实现的夹具。

共享 GPU 压力内核、整数分份、物性求值、存档 codec、宿主几何与客户端数学按用途保留；不能依据 `Cpu`/`Pressure` 文件名批量删除。构建任务 `runCpuValidation` 中的协议／持久化等非仿真用例应迁至符合职责的名称与套件。

完成条件：生产依赖闭包内只有一套时间步进，G3 静态编辑例外已隔离且无步进入口；搜到的 CPU 字样能归属宿主计算、历史记录或明确测试工具，无可选择的 CPU 求解器和隐式回退。

### G6：完整交付及文档同步

按本轮实际改变的风险选择一次连贯验证，复用构建产物和既有证据。将设计书完整步入口改为 GPU，登记状态、编辑和恢复的新职责链；更新 README、运行时、存档、后端参考与验证入口。历史测试结果保留原运行条件，不能改写为新结构的结果。

本轮完成后，当前实施计划再将下一轮切换到能力补全；两份详细计划不维护第二套进度表。

## 6. 验收与性能判定

| 改动风险 | 优先复用入口 | 本轮需回答的问题 |
|---|---|---|
| 常驻状态与候选迁移 | `runGpuResidentStateValidation` | 采用、释放、导出、恢复后仍可推进 |
| 完整游戏操作 | `runGpuProductionDemoValidation` 的 tank/controller/flow | 初始化、编辑、实体、展示、事务沿生产路径完成 |
| 热化学状态保留 | 既有 thermal-phase、solid-liquid、precipitation 场景 | 相变待位移、固气库存、内能在编辑和恢复中保持 |
| 持久事务 | 现有 container、ownership、region-state 用例 | 实际写入后恢复分类和数量无重复 |
| 删除和重组 | 模块编译、现有架构检查 | 无残留依赖，单一生产路径，文件规模合规 |

无需为类移动重跑全部物理矩阵。仅对新失败模式补充测试，例如状态回读途中设备丢失、设备候选完成但外部事务尚未采用。能用现有正常流程回答的问题直接复用。

GPU 数值结果采用守恒、非负库存、真实容量及宏观现象判断；不要求与删除前 CPU 逐格逐位一致。简单独立解析计算可以作为量级与趋势参照，不发展成另一套时间推进器。

性能比较使用相同硬件、输入、物理时长和功能，包括普通步及一次实际编辑／保存恢复成本，区分冷初始化。完整步统计包含必要交接，诊断大量回读单列。现有生产暂停规则保留；64³／50 ms 仍为待评估目标，本轮不以达到该目标作为删除 CPU 的前提。

## 7. 审阅时需要裁决的问题

1. 同布局编辑如何复用候选槽和既有 GPU 内核？明确提案影响范围、需要全域重算的气腔拓扑，以及仅需局部更新的库存字段；分别记录上传范围和实际重算范围。
2. `FluidDomain` 的时间推进依赖是否彻底切断？按 G3 清单列出暂留的编辑拓扑、动量和热账职责，明确 S2 承接者及删除时点。
3. GPU 候选、WAL 与 HEAD 的提交顺序，在设备丢失时是否足以恢复已发生的物品／世界副作用？沿实际协议核对后确定最小恢复数据。
4. 布局定义能否用现有工具小幅集中？若需要大型生成器或表达式框架，退回简单的共享字段声明。
5. 当前 GPU 调度内哪些对象确有独立数据所有权，值得拆出？按此划分，避免只按行数拆文件。

上述问题影响具体实现，不重新开放“保留双完整求解器”的路线。后续能力计划可提出新的物理状态，但须在本轮单一执行、编辑、提交及恢复契约中落地。
