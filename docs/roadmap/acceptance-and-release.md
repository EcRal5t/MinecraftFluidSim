# 里程碑验收与发布门

本文定义未来阶段如何闭合，不是每个小增量的累计测试清单。日常最小门仍只从 [维护路由](../maintenance/routing.md) 选择。

## 每个里程碑必须回答

| 层次 | 必须回答的问题 |
|---|---|
| 物理真值 | 体积、质量、组成、电荷、气体量、动量或能量是否在允许源汇之外闭合？ |
| 数值离散 | 压力残差、CFL、界面权重、密度比、固体法向和 reseeding 是否收敛且无 NaN？ |
| 渲染重建 | 稀薄 marker、多材质界面、指示剂颜色与插值是否可见且不反写状态？ |
| 调度性能 | 活动、降频、休眠、唤醒和 CPU/GPU 切换是否得到同一守恒结果？ |
| 存档事务 | 写入/恢复中断、未知版本、chunk 卸载与玩家编辑是否安全？ |
| 网络协议 | 版本/capability、未知可选段、旧序列、重连与不兼容拒绝是否正确？ |
| 游戏交互 | 容器、控制器、实体、方块更新、多人观察和断线重连是否一致？ |
| 发布资源 | feature flag 关闭/重开是否保留状态，模型、贴图、配方、反馈和中英文本地化是否完整？ |

不受某次改动影响的层只需明确说明“不涉及”，不得因此重跑旧里程碑全部门。

## 按风险升级的验证阶梯

1. 无 Minecraft 依赖的求解器、材料或化学独立回归。
2. 接入游戏边界后才使用 Fabric GameTest 验证方块、物品、存档与恢复。
3. 改计算后端或规模时做 CPU/GPU 容差对照与性能基准。
4. 只有自动门观察不到渲染、真实碰撞或事务时，才使用专用世界人工 smoke。
5. 只有长期稳定性是改动风险时，才做 soak，并记录最大残差、账本误差、marker/mixture 数、显存、GC 与 tick 时间。

当前 CPU 回归由单一 `runCpuValidation` JavaExec 在同一 JVM 内按 selector 调用 `src/test/java` 的可执行验证，并要求 `--offline`。`fast` 是日常短门，`milestone` 覆盖所有领域的短模式，`soak` 只放长期稳定性，显式领域 selector 运行该领域完整门；具体命令见维护路由。`check` 不隐式全跑这些门。在真正需要 GameTest 前，不为测试框架引入未缓存的联网依赖。

验证预算也是架构约束：新增功能先扩展最近 selector，不得按里程碑复制新的 Gradle task；短里程碑集合的 runner 时间应维持在约 10 秒量级。超过预算的新场景必须拆入 `soak`、替换已覆盖场景或说明为何属于新的不可合并失败域。历史选择实验与只打印数据的 diagnostic 一旦被活动生产路径覆盖，删除可执行源码并只在 progress 保存结论。

## 可复现性与报告

- CPU 参考场景固定随机种子、遍历顺序和输入；能稳定逐 bit 时保留该保证。
- 多线程 CPU、不同 GPU/驱动与不同归约顺序按账本、压力残差和场值容差验收，不要求逐 bit 相等。
- 性能/正确性报告必须记录 Mod 与协议版本、后端、GPU/驱动、种子、时间步、容差和可重放输入。
- timestamp 只报告设备执行；调度和超时仍记录 wall time。

## 扩大范围前的硬门

- 代表性静止基准至少 80% 体积进入守恒休眠，且客户端观察不会唤醒；阈值若调整必须有报告。
- 活动 section 数随实际扰动与边界表面积增长，而不是随全部库存线性增长。
- 32³ 方块 GPU 目标有真实容量/吞吐报告，否则据实降低默认区域上限。
- 常规 GPU 步只回读紧凑快照或有界查询，不全量同步 marker 到 JVM。
- 单 section 存档、唤醒和网络快照都有硬上限。
- 跨 chunk 区域不能半加载步进；检查点失败不能暴露混合 generation。
- M0 恢复事务没有未解决路径。
- M6 的 ownership 对照原型、失配恢复、格式风险和迁移评审已经完成；后续每次继续扩大世界范围都必须重新回答同类事务门。

若阶段失败，依次缩小活动区、降低更新率、采用宏观节点/沉积状态，最后才降低空间分辨率。不得先牺牲守恒、删除小体积物质或用渲染隐藏失败。

## 发布语义

- **1.0** 是在 M0、M2、M2.5 基线上完成 M3–M5 的有界工业流体产品：具备多区域、服务器权威物理、基本材料输入输出和重启恢复，可独立发布、测试和维护，不是“演示版”；不要求开放世界河流、海洋、化学、颗粒或完整热力学。
- **2.0 集成线** 已由 M6.0 ownership 设计门与 M6.1 真实世界桥开启；M7–M10 继续在该事务基线上逐项扩展。
- 版本号由实际验收门决定，不因开发次数自然代表成熟度。
