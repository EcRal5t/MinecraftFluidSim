# 验收与发布

本文用于准备发布或验收一个产品阶段。日常修改的测试选择见 [验证指南](../maintenance/validation.md)。

## 根据改动选择验收范围

| 涉及的部分 | 验收重点 |
|---|---|
| 物质与能量 | 体积、质量、组成、电荷、固体量、气体量、动量和能量的变化都有对应收支 |
| 数值计算 | 时间步、压力残差、界面、碰撞、密度比和粒子拆并稳定，结果有限 |
| 渲染 | 稀薄液体、多材料界面、颗粒和温度正确显示 |
| 调度 | 降频、休眠、唤醒和暂停保留相同库存 |
| 持久化 | 中断可恢复，未知格式保留并锁定，区块卸载和玩家编辑得到明确处理 |
| 网络 | 功能协商、序号、重连和拒绝响应正确 |
| 游戏交互 | 控制器、容器、实体、方块更新和多人观察一致 |
| 资源 | 方块、物品、模型、配方、反馈和翻译配套完整 |

先用相关 CPU 测试检查算法和数据。涉及 Minecraft 行为时补充专服、GameTest 或人工场景；涉及后端或规模时增加性能与容差对照。长期稳定性存在风险时运行长场景，并记录最大残差、收支误差、载体数量、内存、GC 和 tick 耗时。

## 保留可复现证据

CPU 场景固定种子、遍历顺序和输入。原有测试保证逐位一致的部分继续保留该要求；并行 CPU/GPU 的比较采用同一库存规则和明确的数值误差上限。

性能报告记录提交号、后端、设备与驱动、种子、网格、时间步、容差和可重放输入。测试结果与被测构建一起保存。

## 扩大模拟范围前

这是未来范围扩张的验收要求，当前能力见 [系统总览](../architecture/system-overview.md)。

- 代表性静态场景至少 80% 的体积可休眠，查询保持休眠状态。
- 活动成本随实际扰动的分区和接触面规模增长。
- 常规 GPU 计算的回读量限定在紧凑快照或有上限的查询范围。
- 每个存储分区的保存、恢复、唤醒和快照都有资源上限。
- 跨区块区域在所需区块全部加载后计算，存档失败保留上一完整代次。
- 世界归属和容器事务在各提交步骤发生异常时，都能确定恢复或锁定。

## 构建与部署

按本次改动选择并完成测试后，在仓库根目录运行：

```powershell
./gradlew.bat clean assemble compileTestJava --offline --no-daemon
```

主模组 JAR 在 `fabric/build/libs/`，可选 probe 在 `gpu-probe/build/libs/`。选择可部署产物时排除 sources JAR。

1. 确认目标 Minecraft 实例和 mods 目录。
2. 将对应 JAR 放入该目录，同一 Mod id 保留一个启用的版本。
3. 比较源文件和目标文件的 SHA-256，例如在 PowerShell 中使用 `Get-FileHash -Algorithm SHA256 <jar路径>`。
4. 按本次发布涉及的游戏场景复核，并保留日志。

原维护环境的 mods 路径为 `Z:\Games\Minecraft\Pure\.minecraft\versions\26.2-Fabric 0.19.3\mods`。其他开发者使用自己实例的路径。
