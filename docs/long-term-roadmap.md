# Real Water 长期产品规格与实现路线

本文记录从 `0.8.0` 有界 3D PIC/FLIP 水体原型走向“可混合、可反应、包含气体和颗粒沉积物的世界流体系统”的已确认需求、技术边界、数据不变量和分阶段验收门槛。它是长期方向文档，不替代 [`maintenance-routing.md`](maintenance-routing.md) 的当前代码路由，也不表示后续存档格式已经冻结。

基线：Minecraft Java 26.2、Fabric Loader 0.19.3、Fabric API 0.157.0+26.2、Mod 0.8.0、Java 25 字节码。活动求解器仍是 [`FlipFluidDomain.java`](../src/main/java/com/example/fluid/FlipFluidDomain.java)，不得切回旧 VOF。现有 `0.8.0` 是路线形成前的历史版本号，不表示已经完成未来 1.0 的 80%。

## 零、发布切割线

**1.0 明确定义为完成 M5 的“选区工业流体”**。它必须包含：M0 世界恢复安全、M2 多区域/控制器/持久化/休眠、M2.5 自由表面基础、M3 多液体/变密度/连通器、M4 表面张力，以及 M5 密闭气体网络/气液压力/汞柱实验。M1 是 1.0 前的 GPU 技术探针，不是用户功能。

1.0 的可玩边界是控制器或开发命令明确圈定的封闭区域。它允许多区域、服务器权威物理、基本材料输入输出和重启恢复，但**不要求接管开放世界河流或海洋，也不要求化学、颗粒沉淀和完整热力学**。这不是“演示版”，而是第一个可以独立发布、测试和维护的产品终点。

**2.0 从 M6 世界 ownership 与真实世界流体接管开始**。M7 化学、M8 颗粒和 M9 热力学在 2.0 之后逐项发布，不阻塞 1.0。版本号按实际完成的验收门槛决定，不再按开发次数自然递增成熟度。

## 一、已经确认的产品目标

最终目标不是把原版“一格一种流体、若干固定液位”做得更平滑，而是让一个 Minecraft 方块空间内可以同时包含不同体积、组分和相态的物质：

1. 液体不受“一物一格”限制，能形成任意高度、连通器和静水压力。
2. 可互溶液体连续混合；不可互溶液体保留相界面并按密度分层。
3. 开放空间使用环境大气边界，密闭或近密闭空间保存气体并产生气压；小孔具有有限流量，不能把“密闭/开放”处理成瞬时布尔切换。
4. 化学物质和反应由数据驱动注册。第一阶段反应按化学计量立即完成，守恒质量、声明的组成和电荷；动力学、平衡、有限溶解度和热效应后续加入。
5. 溶液允许离子。第一阶段只把电荷作为组分属性和守恒量，不求解电磁场。
6. 固态动态只覆盖细沙、沉淀等颗粒物：沉降、悬浮、安息角、反应和低成本沉积；不做通用刚体或弹性固体模拟。
7. 最终希望接管所有已注册流体，但先在显式选区/工业反应区内达到可靠、可恢复和可量化，再扩大到河流、海洋和世界范围。
8. 多人、区块卸载和重启后持久化是正式目标。远处平静区域允许转换为守恒的宏观休眠状态，唤醒时重新播种 marker。
9. CPU 是必备参考和回退后端；Windows + NVIDIA 是首个 GPU 后端支持范围。其他平台属于远期目标。

实现顺序已经确定如下；其中 M1 GPU 探针和 M4 表面张力是插入产品功能之间的技术/质量门槛，因此也在这里显式列出：

1. 完成 0.8 崩溃恢复事务；
2. 完成独立 GPU 管线/压力探针，同时保留 CPU 规范后端；
3. 动态/选区仿真域、休眠、持久化与自由表面基础；
4. 多液体、不同密度、连通器与分层；
5. 表面张力与润湿；
6. 密闭空气、气压与小孔流动，达到 1.0；
7. 完成 ownership 评审后扩大到世界流体接管；
8. 化学组分、酸碱和通用指示剂；
9. 沉淀物与颗粒固体；
10. 温度、相变和反应热。

### 近期明确不做

- 不显式填充和逐格求解世界中所有开放空气。
- 不把每个分子或离子做成独立粒子。
- 不在第一版化学中做弱酸、缓冲液、活度、离子强度、反应速率或化学平衡。
- 不在第一版多液体中做有限溶解度和表面张力；二者必须保留数据和接口位置，后续加入。
- 不先承诺海洋规模 20 Hz。选区反应釜是正式产品阶段，不是失败降级模式。
- 不用吸墙、角落偏置、强制找平或把粒子互相拉拢的经验力冒充压力、润湿或表面张力。

## 二、必须长期保持的分层

每项改动必须先说明它属于物理真值、数值离散、渲染重建、调度策略还是世界事务；不得用下一层修补上一层的错误。

### 2.1 物理真值

物理真值负责回答“存档和传输前后到底有多少东西”：

- 液体 marker 的 `particleVolume` 仍是液体总体积真值。
- 每个可反应混合包保存稀疏组分库存；库存总和是化学物质量真值。
- 每个组分具有每 AU 对应质量、组成向量和电荷；反应前后必须守恒。
- 动量属于运动中的流体/颗粒；温度阶段加入后，内能而不是显示温度成为热量真值。
- 密闭气体区保存体积、气体库存和压力状态；M5 先用固定参考温度，M9 再让内能/温度成为动态真值。
- 稳定沉积物保存物质 ID、数量、孔隙率及必要的混合组成。
- 指示剂只是二值、可随流体移动的显示标记，不具有质量、浓度或反应计量，不得影响密度和守恒。

### 2.2 数值离散

网格和粒子是对真值的数值表示，不得反过来定义总量：

- MAC 面速度和中心压力用于投影；平滑 `volume[]` 仍只是 P2G 重建量。
- 压力流体格仍由实际 marker 占据判定，不能重新用微量核权重扩张相区。
- 多密度液体需要把压力方程升级为变系数形式 `div((1/rho) grad(p))`，而不是给每种物质各求一次压力。
- 可互溶物共享速度/压力场并运输组分；不可互溶物共享机械压力但保留相标签和界面。
- 自由表面、固体切割格和液液界面需要分数面积/体积权重。先验证压力边界，再加入表面张力。
- 固体碰撞仍只限制墙面法向，允许切向沿墙和沿墙角运动。
- 颗粒沉积物可以使用比流体 marker 更小的碰撞半径，但不得仅为它把整个压力网格每轴翻倍。

### 2.3 渲染重建

- 客户端只消费服务端快照，不修改体积、组分、压力或反应状态。
- marker mask 继续作为稀薄流体的内部种子；多材质后扩展为材质/相 palette，而不是删除。
- 混合液颜色由基础溶液颜色按组分连续混合；界面材质不得因密度卷积被当成化学混合。
- M3 的外部自由表面从总液相占据场重建；不可互溶液体的内部界面从分相字段使用 multi-material/partitioned marching tetrahedra 重建。共享界面只生成一次，必须有稳定归属、正确法向且不得产生重合双层表面。
- 有指示剂标记的流体根据当地近似 pH 取得指示色，再与溶液本色混合。
- 调试域默认 `debug true`；正式控制器域默认关闭，可手动打开。
- 表面张力修物理聚集，marker mask 修浅水可见性；两者不能互相代替。

### 2.4 调度策略

降频、休眠和 LOD 只能改变何时、以何种精度更新，不能静默制造或删除真值：

- 活动区域按 CFL 和压力残差执行子步。
- 平静区域先降频，再在速度、压力残差、界面变化、反应和热通量均低于阈值并持续一段时间后休眠。
- 休眠会显式承诺动量近似为零，并保存精确总体积、组分量、气体量和沉积物量。
- 方块更新、邻域通量、实体接触、泵/桶操作、反应条件、温度梯度或压力边界变化都能唤醒。
- Godot 当前 LOD 只减少远处压力迭代，仍让所有粒子全速传输和移动；可迁移其分块压力预算思想，但不能把它当作 Minecraft 休眠方案。
- CPU 参考回归使用固定种子、稳定遍历顺序和可复现输入；并行 CPU/GPU 结果按守恒闭合、残差和数值容差判定，不要求逐 bit 相等。

### 2.5 世界修改事务

- 世界方块修改必须先有可恢复 journal，再执行接管。
- 流体持久化成功发布与原版方块移除必须构成明确事务边界。
- 任何未解决或无法读取的 journal 都必须锁住新的 takeover，禁止覆盖旧恢复数据。
- 新格式必须带版本和迁移器；不得仅因 Java 类结构改变就直接序列化整个域对象。

### 2.6 网络协议

- 从 M2 起，所有快照和交互 payload 都必须带独立的 `protocolVersion`；网络协议版本不能复用 takeover journal 或 region-state 格式版本。
- 登录/配置阶段交换客户端与服务器支持的版本和 feature capability；无法协商时给出可读错误并拒绝进入，不允许错位解码后以“网络异常”断线。
- 每个快照至少带区域 UUID、状态代次/序号、材质 palette 版本和长度明确的可选段。M3 多材质、M5 气压和 M7 指示剂必须通过新增协议版本或已协商 capability 扩展。
- 客户端只接受单调递增且属于当前区域代次的快照；区域重建、后端切换或重连后丢弃旧序列。
- 协议兼容矩阵与 codec 往返测试是发布门槛，不能只在两端同时改 record 字段后手工进服验证。

### 2.7 Feature flag 与发布回退

- 每个未完成里程碑都要有服务器配置门控；新 gameplay 入口在自动测试和迁移测试完成前默认关闭，开发命令仅允许管理员显式调用。
- 注册所需方块/item 可以随 Mod 加载，但禁用时必须拒绝激活、不给世界建立新状态，并保留已有状态的只读恢复/导出路径。
- takeover 范围、控制器上限、GPU 后端、气体网络、化学和颗粒分别门控，不能只用一个总开关。
- 关闭功能不得删除已有物质；只能暂停、落盘、恢复原版状态或要求管理员执行有说明的迁移。

## 三、目标架构

```text
数据包材料/组分/反应定义
        -> MaterialRegistry / ReactionRegistry（装载时验证）

命令、桶、控制器、世界事件
        -> FluidRegionManager（多个区域、预算、生命周期）
            -> FluidRegion（真值、边界、活动/休眠状态）
                -> CpuFlipBackend（参考实现）
                -> VulkanFlipBackend（可选 Windows/NVIDIA 加速）
                -> GasZoneGraph（密闭区、孔洞、环境大气）
                -> ChemistryStep（稀疏组分与反应）
                -> GranularStep（移动颗粒与沉积物）
            -> FluidPersistenceStore（版本化 chunk-section 数据）
            -> WorldFluidBridge（接管、桶、原版行为适配）
            -> SnapshotBuilder（只读客户端快照）
```

现有 `FlipFluidDomain` 先作为 CPU 参考核心演进，不重写、不切回 VOF。等区域接口和 GPU 探针确认后，再把固定数组所有权抽到 `CpuFlipBackend`；抽取前后必须跑同一套回归。

### 3.1 区域

开发阶段继续提供命令创建矩形、边界为墙的暂停域。正式玩法使用一个仿真控制器方块，识别特殊边界方块围成的任意封闭空间：

- 未闭合、跨越未加载区块或超过配置预算时拒绝启动。
- 允许同服多个控制器域，但共享 cell、particle、组分记录、网络和 GPU 内存总预算。
- 区域之间先不直接连通；以后用显式端口或相邻 section 合并协议连接。
- 开发命令域默认显示边界、固体格、压力/相态诊断；正式域默认不显示。
- 跨 chunk 的区域是一个原子生命周期单元。只要任一必需 section 卸载，整个区域必须先生成一致检查点，再一起进入 `UNLOADED`；严禁把缺失部分临时当墙后继续半区域步进。
- 默认不为区域申请永久 chunk ticket，玩家离开加载范围后休眠落盘。以后只允许管理员为受总量、尺寸和时间限制的工业域显式启用 ticket；关闭控制器、失败或超时必须释放。
- 一致检查点失败时区域保持暂停并给管理员可读错误，不能卸载半份新状态或继续物理步。实现可使用短期有界 ticket 完成本次保存，但不得借此变成隐式永久常载。

### 3.2 区块分段持久化

长期存储按 chunk section 分片，而不是按当前 12×8×12 对象存储。每片至少包含：

- 格式版本、区域 UUID、维度和 section 坐标；
- 各物质/混合包的精确体积和组分库存；
- 活动态需要的 marker、速度和相标签，或休眠态的宏观水位/连通信息；
- 密闭气体节点与跨 section 连接；
- 沉积物 palette 和数量；
- 校验和以及写入代次。

该格式命名为 `region-state v1`，与 M0 的 `takeover-journal v1` 是两个独立版本空间。存储采用临时文件/区域文件写入、校验、原子发布；一个跨 section 区域的清单、各分片和 ownership 代次必须能判定是否属于同一完整提交。GPU 缓冲区布局不是存档格式；读取后必须能构建 CPU 或 GPU 后端。

### 3.3 世界 ownership 设计门槛

M6 开始开放世界接管前，必须像 M0 事务一样单独完成设计评审和可丢弃原型，不能直接从“原水换空气”扩展。至少对比两条路径：

1. **代理占位方块**：用无碰撞的自定义方块表达 Real Water ownership；验证放置/破坏、活塞、光照、生物寻路、原版 fluid tick、邻居更新、爆炸、结构命令、chunk 保存和常见 Mod 扫描行为。
2. **空气 + 独立注册表**：方块仍为空气，ownership 存在版本化 registry；验证外部方块编辑、区块加载顺序、registry 与世界失配、崩溃恢复、校验修复和解除接管事务。

选择依据是世界机制兼容性、可恢复性、存档体积和运行时成本，不预先指定胜者。无论选择哪条，ownership、`region-state` 与方块替换都必须共享区域 UUID/提交代次；加载发现不一致时暂停接管并进入恢复流程，不得自动覆盖玩家新方块。

## 四、材料、混合物与化学数据模型

### 4.1 游戏单位

内部使用一致但架空的单位体系：

- `BV`：block-volume，一个完整方块体积为 1 BV；
- `MU`：质量单位；
- `AU`：化学物质量单位，作用类似 mol 但不宣称与现实等值；
- `PU`：压力单位；
- 后续增加 `TU` 温度和 `EU` 内能。

单位可以通过配置调整时间/重力尺度，但同一存档内不能无迁移修改基本比例。每个化学组分仍需声明 `mass_per_amount`，否则无法同时守恒化学计量和流体质量。

液体体积和化学库存都是需要记账的状态，但不能互相矛盾：组分库存决定质量，材料/物相模型根据组成和状态给出参考密度或参考比体积，marker 的 `particleVolume` 表示实际占据体积。混合或反应若按材料定义造成膨胀、收缩或相变，必须产生显式的体积/相态变化源并进入压力步骤；不能暗中改平滑密度来消除不一致。第一阶段可使用可加的参考体积，之后再扩展非理想混合。

### 4.2 三类定义

数据包概念上分为三层，具体 JSON codec 在对应里程碑冻结：

1. **组分（species）**：ID、显示名、组成向量、电荷、每 AU 质量、基础颜色。
2. **物相/材料（phase/material）**：允许的组分、液/气/颗粒类别、密度、黏度、互溶组、表面张力、接触角和相变参数。
3. **反应（reaction）**：反应物/生成物化学计量、允许相态、是否界面接触反应，以及未来的温度/压力/催化条件。

真实元素和虚构科技物质使用同一种组成向量。虚构物质可以声明 `metal`、`oxygen` 等抽象守恒基元。装载器必须拒绝：未知 ID、负质量、未守恒的组成、质量或电荷、矛盾的互溶定义和无界解离循环。

这套分层借鉴成熟化学软件将 phase、species、composition、charge 和 reaction 分开描述的做法，但只实现游戏需要的子集，可参考 [Cantera YAML 输入模型](https://www.cantera.org/stable/yaml/index.html)。

### 4.3 稀疏组分库存

不能给每个 marker 分配 Java Map。建议先实现“局部混合包 + palette handle”：

- marker 保存 `mixtureHandle`、体积、速度和少量标志；
- handle 指向排序后的稀疏 `(speciesId, amountPerVolume)` 记录；
- 相同组成记录可驻留共享，局部反应时 copy-on-write；
- 同格混合和反应后重新合并近似相同记录；
- 睡眠时按 section 聚合，唤醒时按库存重新播种；
- species 数量和各库存使用定点量或等价的精确账本表示。为去重做浓度分箱/规范化时，所有舍入余量必须进入可追踪 residual ledger，并在后续合并或保存时回填；不得以“低于 0.1%”为由静默删除物质或电荷。
- 每区域记录活动 handle 数、创建/合并率、溢出槽和 residual；设置软压缩阈值与硬上限。达到硬上限时暂停或拒绝新的复杂混合并报告诊断，不能继续分配到 OOM，也不能丢弃少数组分。
- 在多物质强搅拌基准中对比 canonical handle、定点分箱 + residual 和“每 marker 固定少量槽 + overflow”；守恒、句柄上限与吞吐均通过后才冻结 GPU 布局。

第一版化学可以在 CPU 上处理被标脏的活动格；不要为等未来 GPU 反应 kernel 而阻塞数据正确性。

### 4.4 离子、酸碱和指示剂

第一阶段使用完全解离的强电解质：

```text
HCl  -> H+ + Cl-
NaOH -> Na+ + OH-
H+ + OH- -> H2O
```

因此“NaNO3 + KCl”和“NaCl + KNO3”完全溶解后会得到同一组离子库存。Na+、Cl- 等旁观离子不会为压力增加独立求解，只参与库存、质量和电荷守恒。

pH 使用由局部 H+、OH- 相对浓度导出的游戏化 0–14 刻度；先不声称现实精度。通用指示剂是独立的二值 marker 标志：

- 添加 item 对准当前可接受指示剂的互溶液相执行一次 flood fill；不跨固体或不可互溶界面。连通体积超过 100 BV 时拒绝，不做部分添加，并在聊天中显示已测得的下限和 100 BV 上限。
- 成功后给该连通范围现有流体 parcel 加标志；标志随原 parcel 移动，不自动复制给后来混入的未标记 parcel。
- 抹除 item 对目标连通范围清除标志。
- 局部有标记和无标记 parcel 并存时，客户端按可见占比混合颜色；该占比不是指示剂浓度或化学真值。

### 4.5 互溶、分层与有限溶解度

第一版只实现：

- 相同互溶组：组分连续混合，密度、黏度和基础颜色按定义插值；
- 不同互溶组：保持相标签，形成液液界面并按密度自然分层；
- 同格反应只在数值混合步骤已经让反应物进入同一局部混合包后发生，不能仅因隔墙或隔界面相邻就反应。

不可互溶相在第一版仍共享一个局部速度场。这是为了先得到分层、翻转和静水压力的刻意简化，不是完整的两流体界面模型：它不能准确表达界面两侧切向滑移、剪切不稳定、液滴破碎或乳化。若这些现象成为玩法要求，必须另立双速度/多速度模型验证，不能用渲染噪声假装完成。

有限溶解度必须作为后续化学里程碑，使用饱和上限、溶剂/溶质规则和析出，而不是以随机概率拒绝混合。

## 五、液体求解路线

### 5.1 多密度压力

当前常密度压力矩阵是连通器的基础，但不足以处理油水、重液体和气液压力。升级顺序：

1. marker 增加材料/相和物理质量，`particleVolume` 继续独立保存；
2. P2G 同时重建面动量、体积和质量；
3. 在 CPU 小域对比面上 `1/rho` 的候选离散：相邻格 `1/rho` 的算术平均、先插值 `rho` 再取倒数、按界面距离/体积分数加权的守恒通量系数；不在路线阶段武断冻结公式；
4. PCG 矩阵使用变系数压力算子；
5. G2P 仍输出一个混合物速度场，物质组分随 marker 输运；
6. 候选离散必须保持矩阵对称正定，并在 1:1、油水和至少 13.6:1 密度比下比较静水误差、界面寄生流、PCG 迭代数与残差；
7. 验证同液连通器等高、不同密度液柱压强平衡和稳定分层。

不得通过给不同液体设置不同重力、强制排序粒子或每 tick 调平来伪造密度效应。

### 5.2 自由表面和表面张力

M2.5 先补分数格自由表面压力权重和长期 reseeding，它们是 M3 变密度静水验证的前置条件。M4 再实现表面张力：使用界面曲率和材料表面张力系数产生压力跳跃/体积力，并用 balanced-force 测试限制伪流；基本思路可参考 [Brackbill 等人的 Continuum Surface Force](https://www.sciencedirect.com/science/article/pii/002199919290240Y/pdf)。

固体润湿通过材料接触角定义，不写死“水喜欢墙”或“浅水互相吸引”。验收至少包含：

- 零重力静止液滴压力跳跃与半径关系；
- 静止液滴无持续伪流；
- 水滴合并和断开时体积守恒；
- 同体积液体在不同接触角表面呈现不同铺展；
- 当前浅水测试在无渲染补丁变化时仍可见且能按物理系数聚集。

### 5.3 实体耦合

当前按浸没比例计算的浮力只是原型。长期实现改为：

- 在实体碰撞表面积分流体压力，净压力自然产生浮力；
- 黏性/形状阻力仍单独计算；
- 实体表面速度作为移动固体边界进入投影；
- 压力和阻力的反作用量传回流体，形成双向动量守恒；
- 实体占据体积挤开等量流体，容量不足时不能静默删除。

压力与刚体联合投影可参考 [Batty、Bertails、Bridson 的变分固液耦合](https://www.cs.ubc.ca/~rbridson/docs/batty-siggraph2007-variationalcoupling.pdf)，但 Minecraft 实体先采用离散表面采样，不要求一次实现完整刚体求解器。

## 六、空气与其他气体

Minecraft 规模下采用“多区域气体网络 + 必要处局部 CFD”的混合设计：

- 一个气体区域节点保存体积、组分库存和近似均匀压力。M5 使用固定参考温度下的简化状态方程；M9 再加入动态内能、温度和非等温过程。
- 外界大气是特殊环境节点，具有配置的参考压力、温度和组成。
- 门缝、小孔、管道和大开口是连接边；流量由压差、开口面积和阻力决定。
- 打孔不会瞬间删除高压气体；开口扩大只会提高有限均压流量。
- 方块变化导致区域分裂时，按原密度/温度和子体积分配库存；合并时总库存和能量守恒。
- 液面从下方压缩气体时更新气体可用体积，并把气压作为液体自由表面的边界压力。
- 射流、火焰或玩家附近需要空间速度场时，才把局部节点展开为细网格；第一版可以只显示方向性喷流粒子而不承诺完整湍流。

拓扑搜索必须有硬预算。控制器域直接以已知边界为搜索范围；对未来没有控制器的天然空腔，增量 flood fill 默认最多访问 512 BV（可配置但受服务器总预算约束）。触达未加载边界、环境连通标记或超过上限时立即视作连接环境大气并停止扩张，不扫描整片矿洞/地表；命令状态和 debug 显示本次访问量、停止原因与最终分类。方块更新只使相邻节点/边变脏，不能每次重建全世界气体图。

这种“区域节点 + 压差流路”不是随意近似；建筑气流模型同样把空间表示为守恒区域和压力相关流路，可参考 [NIST CONTAM](https://www.nist.gov/services-resources/software/contam) 及其[气流路径说明](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir7251.pdf)。

第一阶段空气验收：

1. 完全开放水面等于环境表压；
2. 密闭活塞/液面压缩空气，压力随可用体积单调增加；
3. 高压腔通过一格小孔有限时间排气，不瞬时归零；
4. 开孔、封孔、区域分裂与合并前后气体库存守恒；
5. 重液柱/汞柱式装置能由两侧气压差保持不同高度；
6. 气体混合和未来气相反应复用同一 species 库存。
7. 在超大天然洞穴边缘连续放置/拆除方块不会超过单 tick 搜索预算，也不会把超预算空间误保存为有限密闭气体库存。

## 七、颗粒物与沉积物

Godot 参考中的沙粒采用弹道粒子、半主格支撑链、每半格占位和孔隙容量；它在二维演示可用，但把沙当作流体边界并以经验孔隙排水，不能直接迁移为最终三维水沙压力模型。

分两步推进：

### 7.1 低成本沉积原型

- 颗粒具有物质 ID、体积、质量、速度和反应属性；
- 水中受到重力、浮力和相对速度阻力；
- 颗粒占据的真实固体体积从流体可用体积中扣除，孔隙水仍参与压力；
- 颗粒碰撞半径可小于液体 marker，但压力格保持原分辨率；
- 稳定堆积超过休眠阈值后聚合为沉积物格，停止逐粒计算；
- 沉积物接触到可反应流体时只唤醒反应附近所需数量；无反应时不因失去普通方块支撑自动全量粒子化；
- 反应沉淀与沙共用运动机制，但保留不同材料 ID、颜色、密度和反应规则。

### 7.2 模型选择门槛

低成本模型必须通过水中沉降速度、轻重颗粒浮沉、安息角、孔隙水压力、密闭容器总体积和沉积/再溶解守恒测试。若无法同时通过，不继续堆叠支撑或偏置规则，而是做 MPM/Drucker–Prager 小型验证。MPM 能在粒子与背景网格间处理摩擦性塑性材料，并已有水-沙多相研究基础，可参考 [Pradhana 的多相 MPM 工作](https://escholarship.org/uc/item/52b8b82q)。

## 八、桶、控制器与世界桥接

### 8.1 桶的真值

- 一桶容量为 1 BV。
- 满且纯的原版水仍可使用普通水桶。
- 不满的纯水桶给原版水桶附加 Real Water 数据组件；耐久条只显示剩余比例，Minecraft damage 值不是水量真值。
- 右键放出组件中保存的实际体积；清空后变回空桶。
- 两个不满纯水桶可通过动态配方合并。输出优先填满一桶，溢出量以 recipe remainder 原子地留在指定输入桶。
- 混合液、酸碱和非原版液体使用 Real Water 容器，保存体积、混合物 handle、温度（加入后）和指示剂标志。
- 任何装取、放出、合成、掉落、漏斗移动和玩家死亡路径都必须保持总量。

M6 必须把原版桶边缘行为写成自动化矩阵，而不是只测玩家右键：

| 路径 | 满纯原版水 | 部分纯水 | 混合物/其他液体 |
|---|---|---|---|
| 玩家装取/放置 | 可退化为原版水桶；在模拟区按 1 BV 账本流转 | 保持组件体积，堆叠上限 1；只向模拟区放实际体积 | 使用 Real Water 容器和完整 mixture handle |
| 发射器 | 原版行为必须与 ownership 协调 | 走同一服务端账本，不生成整格水 | 走同一服务端账本；无兼容目标时原样保留并反馈 |
| 合成/合并 | 不额外复制 | 动态配方原子填满，recipe remainder 保存溢出 | 只有材料规则允许时才合并，组分逐项守恒 |
| 漏斗、掉落、死亡、断线 | 保持物品语义 | 数据组件往返不变，不自动合并 | 数据组件/handle 序列化往返不变 |
| 创造模式 | 明确记为非守恒外部源/汇 | 拾取副本不得污染生存账本 | 同左，并在 debug 统计来源 |
| 其他 Mod/数据剥离 | 原版兼容 | 未协商 API 时拒绝转移，不猜测体积 | 未协商 API 时拒绝转移，不展开为原版水 |

如果 vanilla `WATER_BUCKET` 在任一必需路径无法可靠保留数据组件，则改用专用 Partial Water Container。不得为了保留原版物品外观而接受水量复制或丢失。

### 8.2 世界接管顺序

1. 先只接管控制器/命令显式选区，边界为墙。
2. 让纯水在区内真实流动，并完成桶交互。
3. 接入 chunk-section 持久化和休眠，允许选区跨区块。
4. 再接管附近原版河流/水池，并保留恢复事务。
5. 原版灭火、耕地湿润、冲掉方块、岩浆成石等行为逐项适配；不阻塞真实流动首发。
6. 其他 Mod 流体通过数据注册和显式 API 映射；不自动猜测任意 fluid/block 的语义。
7. 海洋和世界生成水最后开放，必须先有压力区域拆分、休眠率和存档体积基准。

世界桥接不应长期依赖“在原水位置持续写空气”。最终需要一个明确的模拟区所有权层，使原版流体 tick、放置和邻居更新知道该位置由 Real Water 管理。

### 8.3 游戏内容与资源账本

控制器/边界块、部分液体容器、指示剂和抹除器进入里程碑时，必须同步提供方块状态、模型、贴图、配方或取得方式、创造标签、本地化名称/tooltip、失败反馈以及必要的声音/粒子。正式发布至少校验 `zh_cn` 和 `en_us`，缺失资源或翻译视为该 gameplay 入口未完成，而不是发布后的美术欠账。

## 九、性能与 GPU 路线

### 9.1 规模事实

当前 `24×16×24` 求解网格有 9,216 个 cell；满水约 73,728 个 marker。`32×32×32` 方块在每轴 2 cell 时是 `64³ = 262,144` 个 cell、约 2,097,152 个满水 marker，约为当前 cell/particle 规模的 28.4 倍。全加载区块再显式填空气远超这一规模，因此必须同时依赖稀疏活动格、休眠和可选 GPU。

当前 `FlipFluidDomain.MAX_PARTICLES = 262_144`，只等于上述 32³ 方块目标的 cell 数，是满水 marker 需求的八分之一。它是 0.8 单域防失控硬上限，不是未来区域容量承诺：M1 的 32³ 探针必须使用独立可配置缓冲预算并实测显存，M2 则把单区域与全服务器 marker 上限显式配置、拒绝超预算创建；不得简单放大一个 JVM 全局数组常量。

### 9.2 活动等级

每个 section/区域采用有滞回的状态机：

- `ACTIVE`：完整子步、压力、粒子、反应和耦合；
- `REDUCED`：仍保留粒子，但按事件和较低频率更新，边界 guard band 保持全精度；
- `HYDROSTATIC_SLEEP`：保存静水/分层宏观状态和精确库存，速度承诺为零；
- `UNLOADED`：状态已校验落盘，不占求解内存。

禁止只跳过 advect 却继续从旧粒子位置 P2G。相邻不同等级的质量、动量和压力通量必须成对记账。

### 9.3 并发边界

Minecraft 世界读取、方块修改和实体列表快照留在服务器主线程。数值求解可以在工作线程/GPU：

1. 主线程冻结本步碰撞、边界和交互输入；
2. 后端处理不可变输入并写下一状态；
3. tick 边界提交完整结果；
4. 超时保留旧完整状态，不展示半步状态；
5. 世界修改仍通过主线程事务执行。

### 9.4 独立 GPU 探针

在主求解器依赖 GPU 前，单独建立一个不修改世界的 Fabric 测试 Mod。Gradle `runtimeClasspath` 已确认 Minecraft 26.2 解析到 LWJGL 3.4.1 的 Vulkan、Shaderc 和 VMA；探针第一步仍须在客户端集成服务器和独立服务器实际加载 Java 类与各自 native，记录模块/驱动版本。探针应复用同版本，不能再捆绑冲突版本。

2026-08-18 检测到的首台基准机为 i5-13400F（10 核/16 线程）、约 32 GB 内存、RTX 4060 Ti 16 GB、RTX 5070 Ti 16 GB，Vulkan 1.4 可枚举两张卡。该记录只定义首轮测试环境，不是永久最低配置。

首期只支持 Windows + NVIDIA，使用无窗口 Vulkan compute。Java 可以通过 LWJGL 的 Vulkan 绑定访问计算 API；Vulkan compute 可独立于图形管线运行，参考 [Vulkan Compute Shader 文档](https://docs.vulkan.org/tutorial/latest/11_Compute_Shader.html) 和 [LWJGL](https://github.com/LWJGL/lwjgl3)。

GPU 只作为服务器权威物理后端，客户端仍消费版本化网络快照；首期不设计客户端与集成服务器共享显存或零拷贝渲染。活动区域的粒子、网格和临时求解向量必须常驻显存，不能每步完整回读 JVM 堆：

- 每次快照周期在 GPU 上压缩出渲染所需的表面/分相字段、marker/solid mask、palette 索引和诊断摘要，只回读紧凑 payload；CPU 后端生成同一协议 schema。
- 桶、实体和方块交互优先使用有界格/区域查询，不以读取全部 marker 为前提。
- 完整状态只在 checkpoint、休眠、卸载、后端迁移或诊断导出时异步分片回读；回读期间使用代次校验，不能把跨步分片拼成同一个存档。

探针必须依次验证：

1. 客户端集成服务器和独立服务器均能加载 Vulkan/Shaderc/VMA 类与 native、枚举设备、创建 compute queue 并正常卸载；
2. 可配置选择 RTX 4060 Ti 或 RTX 5070 Ti，设备缺失时自动 CPU 回退；
3. SSBO 上传/下载、3D dispatch、barrier、整数原子和所需浮点特性；
4. 3D clear、P2G、grid prep、压力迭代、project、G2P、advect 和快照压缩/稀疏回读的最小管线；
5. 在 CPU 先完成 5.1 的面系数离散对照，再在 GPU 对比 PCG 全局归约、red-black Gauss-Seidel/SOR，以及至少一种多网格或预条件路线；同时报告每轮 dispatch/barrier 成本、残差曲线和大密度比稳定性，不默认照搬 CPU PCG 或 Godot Jacobi；
6. 与 CPU 小域对照：体积相同，压力/速度在规定误差内，固体法向和相分类一致；
7. 分别测量完整状态回读与压缩快照回读，并证明常规物理步不把全部粒子复制到 Java heap；
8. 测出 CPU/GPU break-even 规模；当前 12×8×12 方块域以“争取明显快于 CPU”为目标，但小域提交开销不能单独否决 GPU 路线；
9. 争取让 32×32×32 方块、每轴 2 cell 的水体管线达到 20 Hz；未达到则按实测降低正式上限；
10. Minecraft 渲染同时运行 30 分钟无驱动重置、无 Vulkan 资源泄漏、无服务器 tick 死锁；
11. 探针不包含 takeover、存档写入或不可逆世界修改。

GPU 浮点执行不要求逐 bit 等同 CPU，但守恒量必须满足同一上限，CPU 参考场景必须决定“物理正确”，不能让 GPU 结果反过来成为规范。Vulkan 不可用、初始化失败或运行时设备丢失时暂停受影响域并从最近 CPU 可读检查点恢复，不得继续使用不完整缓冲区。

## 十、分阶段实施与验收门槛

版本号在实际发布时再定；以下里程碑顺序比名称重要。任何阶段都要同时给出物理真值、数值离散、渲染、调度/性能和存档/事务测试。

### M0：完成 0.8 takeover 事务

先保持现有 `takeover-journal v1` 可读，不贸然改格式：

- 正常 takeover 前 journal 必须创建，正常 remove/关服恢复后必须删除；
- journal 已存在或启动恢复失败时锁住新 takeover，防止覆盖旧备份；
- 把 journal codec、原子发布和世界修改调用隔离成可注入接口，并设置命名故障点：写入前、原子发布后、移除第 N 个方块后、恢复第 N 个方块后、删除前；只做事务所需的窄边界，不先实现通用虚拟文件系统；
- 验证每个中断点重启后幂等恢复，且不覆盖玩家实体方块；
- 测损坏 NBT、未知版本、维度暂未加载、临时文件残留、原子移动不可用和删除失败；
- 在 NBT 成功发布后、修改世界前，同时原子写入人类可读的 `realwater-takeover-WARNING.txt`，说明未恢复前不得卸载/降级 Mod，并记录世界、维度、方块数和恢复步骤；完整恢复或确认未修改世界后才删除。它不是恢复真值，不能代替 NBT；无法写警告时拒绝 takeover；
- 明确接受一个无法由代码消除的残余风险：管理员若带着未解决 journal 强行移除或降级到不认识 journal 的版本，Mod 已无法自动恢复。README、命令反馈和警告 sidecar 必须要求先 `/realwater remove` 或完成启动恢复并保留世界备份；
- 当前启动恢复使用 `Block.UPDATE_ALL`；加入恢复点邻接下落沙/砾石、原版水、红石和其他会连锁更新方块的冒烟，记录更新数量并证明没有无界级联。是否缩小 update flags 必须根据该测试决定，不能只为静默恢复而跳过必要邻居一致性；
- 若需要 `takeover-journal v2`，必须先实现 v1 reader 和原子迁移，说明风险后再改存档格式；
- 修正 README/日志，使 takeover 的世界修改边界准确可见。

完成条件：自动测试通过，加一次真实世界的创建、正常删除和强制中断恢复冒烟测试；测试世界保留备份。

### M1：GPU 能力探针（不进入正式存档）

按 9.4 建立独立测试 Mod，并生成运行时模块/native、设备、求解算法、吞吐、显存、全量/压缩回读、CPU 对照和稳定性报告。CPU 小域同时完成变密度面系数候选实验；GPU 比较 PCG、red-black GS/SOR 与多网格/预条件路线。32³ 满水场景必须实际分配约 210 万 marker，而不是继承当前 262,144 上限后只测八分之一装填。M1 可以与 CPU 区域设计并行调研，但主 Mod 不得在探针完成前把存档格式绑定到 GPU 缓冲区。

### M2：多区域、选区控制器、持久化与休眠

- 实现跨 chunk 区域原子检查点与整域 `UNLOADED`；默认不持有永久 chunk ticket，并测试保存失败路径；

完成条件：反复休眠/唤醒/重启后水量不变；方块更新和实体进入可靠唤醒；任一关联 chunk 卸载时不发生半区域步进；未加载区不占粒子内存；协议不兼容能被明确拒绝而非错位解码。

### M2.5：自由表面基础与守恒 reseeding

完成条件：静水自由表面压力、体积守恒和长期 marker 分布达到规定容差；M3 开始前不得留下已知的一阶自由表面压力边界错误。

## 十一、统一测试矩阵

| 层次 | 每个里程碑必须回答的问题 |
|---|---|
| 物理真值 | 体积、质量、组成、电荷、气体量、动量或能量是否在允许的源/汇之外严格闭合？ |
| 数值离散 | 压力残差、CFL、界面权重、密度比、固体法向和 reseeding 是否收敛且无 NaN？ |
| 渲染重建 | 稀薄 marker、多材质界面、指示剂颜色和插值是否可见且不反向改状态？ |
| 调度性能 | 活动、降频、休眠、唤醒、CPU/GPU 切换是否得到同一守恒结果？ |
| 存档事务 | 写入中断、恢复中断、未知版本、区块卸载和玩家编辑是否安全？ |
| 网络协议 | 版本/capability 协商、未知可选段、旧快照序号、断线重连和不兼容拒绝是否正确？ |
| 游戏交互 | 桶、控制器、实体、方块更新、多人观察和断线重连是否保持一致？ |
| 发布资源 | feature flag 关闭/重开是否保留状态？方块/item 的模型、贴图、配方、反馈和 `zh_cn`/`en_us` 是否完整？ |

测试层级：

1. 无 Minecraft 依赖的求解器/化学独立回归；
2. 引入后使用 Fabric GameTest 做方块、物品、存档和恢复测试；
3. CPU/GPU 同场景容差对照与性能基准；
4. 专用测试世界的手工冒烟；
5. 长时间 soak test，记录最大残差、守恒误差、marker/mixture 数、显存、GC 和 tick 时间。

当前仓库没有 JUnit 或 GameTest 测试依赖，现有 `FlipFluidDomainValidation` 等回归是 `src/test/java` 下可执行的 `main()` 类，构建又要求支持 `--offline`。因此 M0 的 codec、文件和故障注入测试先沿用这一零新增依赖约定，并保证 `compileTestJava` 离线通过；不得为了测试框架先引入缓存中不存在的联网依赖。GameTest 是需要单独建立并验证运行任务的后续测试层，接入后固定版本并保留独立 main 回归作为快速数值基线，不能把尚不存在的基建写成 M0 前提。

CPU 单线程参考场景固定随机种子、遍历顺序和输入，能稳定逐 bit 时保留该保证；多线程 CPU、不同 GPU/驱动和不同归约顺序按场景定义的体积/质量/组分/电荷 ledger、压力残差和场值容差验收，不把逐 bit 相等当作跨后端条件。每份性能/正确性报告必须记录 Mod/协议版本、后端、GPU/驱动、种子、时间步和容差，失败时能重放同一输入。

## 十二、可行性判断与停止条件

这个目标在“选区工业系统 + 活动区域 + 宏观气体网络 + 休眠持久化”边界内有明确可行路线。当前不能承诺的是所有已加载海洋和空气都以同样细度、20 Hz、CPU 实时运行。

扩大范围前必须满足：

- 代表性静止测试中至少 80% 的体积能进入休眠，且不会因客户端观察被唤醒；该阈值可随基准报告调整，但必须在扩大范围前量化；
- 活动 section 数与实际扰动表面积相关，而不是与整个水体体积线性相关；
- 32³ 方块 GPU 目标有真实报告，或已经据实降低默认区域上限；
- GPU 常规物理步只回读紧凑快照/有界查询，不把完整 marker 状态同步回 JVM；
- 单 section 存档、唤醒和网络快照均有上限；
- 跨 chunk 区域不会半加载步进，失败检查点不会产生混合代次；
- M0 世界恢复事务没有未解决失败路径；
- M6 扩大世界范围前已经完成 ownership 原型评审和失配恢复测试。

若某阶段失败，回退顺序是缩小活动区、降低更新率、采用宏观节点/沉积状态、最后才降低空间分辨率。不得先牺牲守恒、删除小体积流体或用渲染假象隐藏物理失败。

## 十三、接下来三项实际工作

1. 为 `takeover-journal v1` 增加未解决备份锁、独立 codec/文件测试和窄接口安全故障注入，完成真实世界中断恢复冒烟。
2. 建立独立 Windows/NVIDIA Vulkan Fabric GPU 探针，输出本机两张 GPU 的运行时模块、求解算法和回读管线对照报告；探针不修改世界。
3. 在 CPU 参考路径设计 `FluidRegionManager` 和 chunk-section 状态，不改变当前 PIC/FLIP 不变量；M0 与 GPU 探针结果通过后再开始持久化格式评审。

这三项都完成前，不扩大 takeover 范围，不改变世界长期存档格式，也不把 GPU 设为必需运行条件。
