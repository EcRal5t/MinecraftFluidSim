审查日期：2026-10-22。源码基线：`630a8e0`，生产代码对应此前的 `cb925f9`。本报告只列问题。

**结论：当前不宜把 M10 的完成声明等同于“守恒职责已经完整整合、维护和排障成本已大幅降低”。** 已复现内部沉积凭空增加总能量的正常流程；其根因正是相同物理交接仍分散在不同提交路径。压力与库存的空间归属仍不一致，长期旋转验收和数值能量误差观测也有缺口。这些问题会继续产生跨文件排障。

## 1. [P1，实测] 颗粒形态转换后的排水遗漏液体势能结算，总能量增加而热账仍闭合

**位置：** `solver/src/main/java/mmm/fluid/GranularTransitionStage.java:19–70`、`GranularLiquidDisplacement.java:35–85`；对照 `CellMacStage.java:400` 的正常输运，以及 `MechanicalEnergySettlement.java:105–117`。

正常力学输运调用 `MechanicalEnergySettlement.prepare`，其中按实际整数质量路线结算液体格心势能变化，同时扣回气体绝热功。沉积、起动、床层松弛结束后走的是另一条路径：

```text
GranularTransitionStage.step
  → 先执行颗粒/床层转换
  → GranularLiquidDisplacement.commit / prepare
  → 共同容量输运、动量混合热、气腔绝热功
  → publish
```

这条路径只把动量混合热加入液体库存，没有进入共同机械能计划。颗粒侧的 `GranularBedPotential` 只计算颗粒和床层的势能；`DomainStep.granularDepositEnvironment` 同样没有为排开的液体支付势能。因此，沉积挤水向上时，颗粒势能损失可以全部转热，水又额外获得势能。

### 正常夹具复现

复用 `fabric/src/test/java/mmm/fluid/GranularBedWakeValidation.java:384` 的私有 `fixture()`：8×8×8、h=0.5 m、dt=0.05 s，已有湿沙床和一颗下落代表颗粒，正式材料、化学与热能力。通过临时同包 Java 程序反射取得夹具，每步调用：

```java
backend.evaluate(new FluidStepRequest(
    step, domain.captureAuthoritativeState(), List.of(), false, 0, true));
```

无实体输入，关闭相变以隔离机械过程。用实际库存内能差、MAC/颗粒动能差和模型自身的势能差计算 `ΔE = ΔU + ΔK + ΔPE`。

| 观测 | 结果 |
|---|---:|
| 首三步的单步总能量误差 | −3.44×10⁻⁶、−3.74×10⁻⁷、−4.50×10⁻⁶ J |
| 第 202 步（零基编号 201） | 一颗粒沉积 |
| 该完整步总能量增加 | **0.571307835 J** |
| 到该步的累计增加 | **0.571347164 J** |

进一步在同一前态执行机械子步后，单独测量 `granularTransitionStage.step()`：

| 沉积阶段实际变化 | 数值 |
|---|---:|
| ΔK | −0.000939592 J |
| ΔPE，液体与颗粒合计 | −3.010625831 J |
| 其中液体 ΔPE | **+0.571309538 J** |
| ΔU | +3.582874418 J |
| ΔU + ΔK + ΔPE | **+0.571308995 J** |
| `exactInternalEnergy().equals(thermalAudit().expectedInventory())` | **true** |

误差与遗漏的液体势能吻合，相对于该次约 3.58 J 的转热也不可归为浮点微差。重复转换没有对应的差额回收机制；本实验确认一次系统性增能，未将其外推成已实测的长期发散。

同一路径还用 `planAfterLiquidDisplacement` 计算气腔绝热功，并把它登记为 mechanical work，却没有正常力学路径中的反向功结算。不同气腔体积发生变化时存在同类遗漏；该分支由代码确定，本次没有另外测量量级。设计书声称这条路径的“反向功由共同机械能计划结算”，与实际调用不符。

**整改方向：** 把内部颗粒转换与液体排水的 K、液体 PE、固体 PE、气腔 U 作为同一份未来状态结算。明确外部插入做功与内部转换的区别，复用共同提交。直接增强现有湿沙床测试，在实际转换步比较独立的总能量，不能只核对 U 与热账相等。

## 2. [P2，代码确定] 固定墙隔开的开放分量仍共用液体压力与整格惯性

**位置：** `PressureFaceGraph.java:70–87、211–216`，`PressureSystem.java:15–18、91–97`，`CellMacStage.java:224–243`，`CellMomentumTransport.java`、`MacMomentumAdvection.java`。

库存 Key 使用 `(cell, material, supportMask)`，但压力未知量按 `cell` 编号。`pressureSupports[cell]` 把各分量合并为位掩码，`pressureAtMicro` 对不同满液分量都返回同一个 `cell` 行。格面惯性也始终为相邻两格全部液体质量之和的一半，没有按该面的实际连通分量分配。

例如，一个切格有两个不相通的开放分量，分别接入两条独立液路：即使库存输运不会穿过固定墙，两路仍共享该格的压力自由度；往其中一路加重液体，也会改变另一侧格面的惯性。若两条液路延伸到多个格，这个耦合影响会传播到已解析尺度。

流体专题已经声明“同格断开液体采用共同 MAC 速度近似”，但这同时压缩了独立压力和惯性，误差受另一分量的装量、密度与压力控制，不能仅用亚格形状误差描述。当前“真实固定墙隔离、同格独立气腔”的使用预期与这种力学自由度不相容。气腔拓扑独立也不足以消除液体压力行的间接耦合。

**整改方向：** 明确支持的切格结构，并让独立液路的库存、压力及惯性采用一致的连通归属。可以限制无法独立表达的结构，也可以只为实际分裂单元保留必要自由度；继续在面面积、静水参考和容量修正上分别添加特例，会扩大表示冲突。

## 3. [P2，诊断与模型风险] 力积分误差可以取用整片流体的显热，缺少独立的误差量级观测

**位置：** `PressureSystem.java:232、308–313`；`MechanicalEnergySettlement.java:77–165、224`；`model/src/main/java/mmm/thermal/ThermalStateFunction.java:46–99`。

压力阶段记录施力前后实际动能差，共同机械能计划再加入格心势能差和气腔功。其余差额整体交给连通机械体：正值按热容加热，负值按各载体可用显热扣除。此连通关系还能通过同一气腔、压力接触和颗粒接触扩大。

因此，压力预测、容量修正或体力离散造成的数值增能，可以通过降低流体温度获得支付；支付额度主要由流体的总显热决定。常温水的显热远大于一次玩家扰动的机械能。总能量和热账闭合，不能单独说明机械误差小，也不能说明局部温度响应可信。

体平均压力功属于文档允许的近似，本条不要求恢复逐点精确热力学。问题在于：目前无法从正常成功步区分“实际物理交换”“可接受的离散修正”和“过大的数值增能被 U 抵扣”。`failureContributions` 仅在热分配已经失败时才生成分项，正常长期运行没有相应累计观测。局部错误可以延后到远处载体冷却、相变异常或显热耗尽时才暴露，增加排障跨度。

现有压缩平面长跑只约束其特定初态的净能量、U 增量和撤力衰减；它没有证明复杂温差、多个气腔和床层转换下的这项误差保持有界。本次没有实测热对流失稳，故不将该风险写成已发生的对流缺陷。

**整改方向：** 在既有机械审计中保留独立的数值修正累计量和主要来源，结合实际机械输入评价量级；给正常受迫流动与撤力过程一个可观察的误差预算。使用诊断数据判断是否需要改离散，避免再加一套复杂的运行时认证层。

## 4. [P1，维护目标] 组合处理器仍共享整个可变域，准备与提交规则缺少单一入口

**位置：** `FluidDomain.java:44–127、226–231`；`DomainFlowFields.java:150–158`；`PressureSystem.java:57–79`；`GasTopologyCoordinator.java:103–116、392`；`CellMacStage.java:269、400`；`GranularLiquidDisplacement.java:40`；`MaterialTransferPlanner.java:284–324`。

当前六个 Domain 处理器和多数物理阶段都持有完整 `FluidDomain`，可以直接访问库存、气腔、热状态、动量、其他处理器及失效标记。职责分文件后，读写权限和准备顺序仍通过共享字段隐式约定。

典型准备调用链为：

```text
DomainFlowFields.ensureGrid
  → PressureSystem.prepareGeometry
    → DomainFlowFields.ensureInventoryGrid
    → GasTopologyCoordinator.refresh
      → 准备/提交气腔及热状态
  → ensureVelocityGrid
```

一个名称像“准备网格”的入口同时牵涉库存派生、气腔初始化或提交、压力分类和速度恢复。单纯读物性、执行编辑、恢复候选的调用者必须知道哪些准备入口可能改变状态，以及旧气体来源必须保留到哪个时点。

提交又分别存在正常输运、外部动量写入、材料转移、颗粒排水、固相插入和相变等分支。各分支自行组合 `requireCurrent`、热账、库存提交、动量提交、失效与气腔提交。第 1 项就是其中一条分支漏掉共同规则的实证。

静态统计也反映这种访问范围：`DomainStep`、`DomainPhaseInventory` 各直接引用 45 个不同的 `domain` 成员，`FluidDomainStateMapper` 引用 38 个，`CellMacStage` 引用 31 个。统计仅计算 `domain.<成员>` 的不同名称；这些数字本身不是错误，问题是改一个交接规则仍需沿多条分散路径逐个查漏。

**整改方向：** 以一次实际物质变化为单位集中准备和发布库存、动量、占容、气腔、能量与失效；各业务入口提供自身的增量和外部功。派生查询与会提交权威状态的操作使用明确入口。复用现有 Plan 和处理器完成集中，避免再机械拆出更多转发类。完成条件应包含“同一规则改动只修改一个所有者、所有入口自动继承”，当前的文件数和类行数检查覆盖不到这个目标。

## 5. [P2，验收缺口] 旋转长期表现没有被当前完整入口证明，部分必要场景漏跑、重复场景仍在

**位置：** `fabric/src/test/java/mmm/fluid/FlipFluidFreeSurfaceValidation.java:114–129`、`LiquidMacroscopicMotionValidation.java:13–20、48–63、88–111`、`GranularBedWakeValidation.java:145–149`；`fabric/src/test/java/mmm/validation/CpuValidationSuite.java:164–180`。

当前光滑涡旋测试的 dt 为 0.001 s，只运行 40 步，覆盖 **0.04 s**。另一旋转测试只运行 4×0.025 s，即 **0.1 s**，允许角动量损失 20%。这些断言不能支撑玩法时长上的旋涡持续性与累计耗散结论。验证指南仍描述完整自由面入口包含“一秒、四秒、多网格旋流”，当前该入口没有对应调用。

`full` 中的 `cell-inventory` 固定调用 `joint-moments`，不会运行 `translationAndMaterialTransport` 的多方向、多格长平移组合。L 形场景由 `MarkerPressureValidation` 间接运行，不能因此推定平移组合也包含在 `full` 中。正式完成记录需要逐项对应实际调用范围。

湿沙床连续场景主要检查 `U == audit.expectedInventory()`，未覆盖内部形态转换的独立总能量闭合，第 1 项因此可以通过现有热账断言。压缩平面长跑中，压力迭代数只输出，未见对应迭代上限的独立验收断言；实施计划“恢复迭代上限断言”的表述需要与具体入口核对。

与此同时，`controllerEmptyThenBoundaryPourPreservesGasAcrossBackend` 同时经 `controller-gas-lineage` 和 `ProductionFluidReplayValidation.main` 进入完整组合。选择器去重只针对领域名称，不会去重领域内重复场景，仍有重复执行长流程的成本。

**整改方向：** 重整既有入口映射，使长期旋转、必要平移组合与内部转换能量各有一个明确归属；为聚焦入口保留可复用方法，完整组合调用一次。改写现有断言即可，无需堆积新测试类。把源码实际运行时长、调用范围与验证指南同步。

## 7. [P1，代码可确定] 熔化按整格容量批准批次，却把全部液体产物放入单一开放分量

**位置：** `solver/src/main/java/mmm/fluid/CondensedPhaseChangeStage.java:175–198、252–274`；`GasComponentCapacity.java:72–78`；`CellRemapMicroTopology.java:35–64`。

`propose` 用固相总质量、总体积和整格剩余空间限制熔化量；只有相变总体积增大时才检查整格容量。`melt` 随后选择剩余空间最大的一个固定开放分量，把本次全部熔化产物加到该分量。它既不按目标分量容量限制批次，也不把产物分配给多个可接收分量。用于挑选目标的 `bitCount(component)/8 - liquidVolume` 还遗漏了剩余 coherent 固相与颗粒占容；实际气体几何稍后才扣除这些占容。

可直接构造的容量反例：一格只有两个互不连通的单微盒开放分量，各容积为 0.125 个标准格体积；格内固相总占容为 0.20，热量足够，本次熔化后液体为 0.18、剩余固相为 0。整格总容量 0.25 足够，收缩型相变可通过 `propose`；`melt` 却把 0.18 全放进容量 0.125 的一个分量。后续 `GasComponentCapacity.availableVolume` 必然遇到负干容并抛出 `Liquid inventory exceeds its open component capacity`。具体批次可由注册表配置；这里说明一般容量逻辑，不声称内置水的一次默认批预算就能达到该数值。

同一职责缺口还体现在空间归属：冻结把不同支撑上的来源聚合为 `(cell, phase)` coherent group，熔化再根据当时最大空位选择支撑，无法保留原来源所在的独立孔隙。即使容量刚好够，也可能把物质交给隔墙另一侧。第 2 项涉及压力自由度，此处涉及实际物质交接与候选能否提交，应分别修复。

**影响：** 合法切割格、固液共存和容量收缩场景可以因目标选择失败而中断整步；整格守恒成立并不足以保障各独立空间可容纳库存。这是会触发后续几何异常的跨模块问题。

**整改方向：** 固相空间归属与熔化目标采用同一套固定开放分量规则，在数量准备时就联合分配目标容量，使用扣除未来固相和颗粒后的真实孔容。若仍采用整格固相近似，必须同时明确、实现其合法分配规则，避免把容量失败留到气腔重建阶段。

## 8. [P2，代码可确定的停滞条件] 气液相变在整批可执行性确定前只选一个候选，零批次候选能长期挡住其他界面

**位置：** `solver/src/main/java/mmm/fluid/GasLiquidPhaseChangeStage.java:118–163、166–187、354–357、479–493`。

当前先用 `selected: cell → Proposal` 保留每格压力失衡绝对值最大的一个候选，再按气腔及组分运行 `closeChamber` 和整数批次分配。压力差越大不代表实际可转换批次越多；后者还受气腔压力响应、液体热容、潜热和联合平衡限制。选中的提议最终可能小于一批，`quantize` 的 `floor(requested)` 把它变为零。此前被丢掉的其他支撑、气腔或材料候选不会重新进入分配。

具体停滞条件：同格有两个合法接触候选 A、B。A 的压力差绝对值较大，其所在气腔组的平衡请求小于一批；B 压力差较小，却能执行至少一批。代码选择 A 后产生零操作，把 B 丢弃。在没有其他状态变化时，下一步仍作相同选择。凝结候选的 `hasIntegerExchange` 直接返回 true，不能提前排除这一条件；`propose` 的 `high >= 1` 只证明库存与容量够一批，没有证明气腔平衡允许一批。

**影响：** 合法相变可因候选竞争长期停住，特别是同格多材料或独立气腔。返回的零操作也不能区分真正平衡和被无效候选遮挡，排障者容易误查热量、气容或饱和曲线。

**整改方向：** 保留候选至气腔响应和整数可执行性确定后再处理同格热量竞争；至少让零批次候选退出并允许其他候选参与。不能用细调压力差阈值修复这种选择顺序问题。相同 LTE 热量约束应由联合分配负责，避免另加一套材料优先级补丁。

## 9. [P2，故障隔离与诊断] 单个气体表示失败会静默取消全域相变，正常接口得到“零操作”

**位置：** `solver/src/main/java/mmm/fluid/GasLiquidPhaseChangeStage.java:249–255、278–281`；`model/src/main/java/mmm/fluid/air/GasInventory.java:19–25、92、190–197、275、314`。

汇总旧节点与新生气体、以及准备相变后气体拓扑时，两处捕获 `GasInventory.RepresentationException`，直接返回 `GasThermalPhaseStats(0,0,0)`。这种异常包含组分槽、物种槽、整数列溢出或正份额无法表示质量列等原因，并不表示热力学平衡。

返回发生在全域相变计划层：一个气腔的表示限制会连带取消其他互不连通、库存与热量都合法的气腔提议。异常的节点、组分、实际容量、提议量及原始原因全部丢失。若原始状态不变，下次依然准备同一整批、遇到同一失败并返回零；上层无法从相变统计看出这个循环。

**影响：** 稀有表示问题被放大为全域相变停滞，表面表现与“没有可执行相变”相同。这直接违背本轮减少无止境排障的目标，也使正常零操作统计不足以证明连续相变没有卡住。此项没有声称已经在内置标准场景实测触发，但失败后的取消范围和信息丢失由控制流明确决定。

**整改方向：** 在数量候选阶段明确处理可表示量，并按实际独立气腔限定失败影响范围；不可恢复的失败保留结构化原因和原始异常，交给既有失败重放入口。保留原库存的事务要求与失败可观测性同时实现，避免吞掉原因后伪装成正常零操作。

## 11. [P1，实测] 异温气腔孔流的压力预测与焓搬运不一致，制造压差反向和不可恢复的温度偏差

**位置：** `model/src/main/java/mmm/thermal/GasEnergyStore.java:152–184、341–355`；`model/src/main/java/mmm/fluid/air/GasOrificeFlow.java:9–59`、`AirNetwork.java:376–442`。

`GasEnergyStore.thermodynamics` 用每个节点自己的状态计算压力储容 `Cᵢ = Vstd,ᵢ / Kadiabatic,ᵢ`。`GasOrificeFlow` 用这些储容组成对称的压力方程，求出标准体积通量；随后 `planFlow` 按供体温度搬运焓。对接收腔而言，流入气体引起的压力增量取决于流入焓，不能用接收腔原温度下的储容代替。热气流入冷腔时，两套计算对同一笔通量预测出不同的终态压力。

`AirNetwork` 后续只按供体库存与正温度余量缩放流出量，没有联合求解搬运后内能、库存与实际状态方程。线性压力解没有反向，并不能阻止实际提交后的压力反向。

### 复现参数与结果

沿用 `fabric/src/test/java/mmm/thermal/GasTransferValidation.java` 的简单气体建模方式：单组分，标准密度 1 kg/m³，定容比热 718 J/(kg·K)，参考温度 300 K、参考比内能 0，热容段覆盖 1–2000 K。两个固定容积气腔各 0.125 m³，无环境端口、无热源、无相变；初始绝对压力为 1.1、0.9 个标准大气压，温度为 900、300 K。孔面积为 0.0625 m²，流量系数 0.65。该面积等于 h=0.5 m 时一个微面的面积。

初始标准气量按 `V × (P/Pstd) × Tstd/T` 设置，内能通过实际 `GasThermalModel.internalEnergyAtTemperature` 和 `planInventoryEnergy` 提交。循环直接调用：

```java
network.stepEdges(dt, energy.thermodynamics(network),
    batch -> energy.planFlow(batch, network));
```

三个实验使用相同初态，运行到 0.5 s；初始压差均为 **20,265 Pa**：

| 时间步 | 第一步实际压差 | 0.5 s 时原热腔温度 | 0.5 s 时原冷腔温度 | 0.5 s 时压差 |
|---|---:|---:|---:|---:|
| 0.05 s | **−9,629.00 Pa** | **828.330 K** | 331.683 K | −4.93597 Pa |
| 0.005 s | **−5,750.80 Pa** | **844.753 K** | 329.116 K | −0.00356827 Pa |
| 0.00005 s | +18,561.3 Pa | **872.503 K** | 325.088 K | −0.00365126 Pa |

三个实验总内能变化均在约 `4×10⁻¹² J` 内。粗步长第一步已经把压差推过零，反向幅度达到初始压差的约 47.5%，下一步开始人工回流。该孔流模型没有气体动量状态，因此这里没有惯性振荡机制可以解释反向。

还有独立的模型内参照：相同气体、相同固定容积、总能量不变时，连续孔流的平衡绝对压力为两腔初始压力的平均值；源腔绝热排气满足

```text
T源,平衡 = T源,初始 × (P平衡 / P源,初始)^((γ−1)/γ)
```

本材料 γ≈1.48140，给出 **872.552 K**。细步长接近这一结果，0.05 s 的终态低约 **44.22 K**。继续等待压差归零不能撤销人工回流造成的质量和温度重分配；0.005 s 同样留下约 27.8 K 偏差。这超出了微量守恒误差，也与单纯的流速离散误差不同。

**影响：** 温差驱动的工业气路、热气充冷罐等正常过程可以在压力近乎平衡后留下明显错误的热状态，并影响下一步相变和压力响应。实验确认有界但错误的松弛终态，未声称已经实测无限发散。现有同温孔流夹具与总内能闭合断言不能暴露该问题。

**整改方向：** 用同一批真实组分、质量和供体焓构造压力响应，使通量求解与最终 N/U 状态方程一致；必要的非线性迭代应同时处理质量和能量。增强现有孔流场景，覆盖异温两腔的压差方向和模型内平衡温度。仅收紧正温度余量、压力残差或要求极小时间步，不能修复这两套响应公式的不一致。

## 12. [P1，功能缺口] 气体没有接入导热，设计书承诺的气腔壁热交换缺少执行路径

**位置：** `solver/src/main/java/mmm/fluid/ThermochemistryPipeline.java:28–33`、`LiquidThermalConduction.java:13–17`、`GasTopologyCoordinator.java:434–438`；`model/src/main/java/mmm/thermal/ThermalCellOperations.java:54–141`、`ThermalCarrierTransport.java:60–61`、`ThermalDomainState.java:931–944`；`docs/architecture/thermal-state.md:234`。

正常导热从 `thermal.carrierAccess(...)` 构建载体批次。`ThermalCellOperations` 的全部载体只有液体、coherent 固相、活动颗粒和沉积物；`carrierCount`、物性、质量、读写内能的分派都没有气体。仅有气体的区域因此得到空批次，并在 `conductionBelowResolution` 中直接返回 true。即使区域内还有液体或固体，接触图也没有气体接收端。

气体处理器的 `step` 则只执行气孔通量及其焓搬运。`GasEnergyStore` 的压缩、重映射、相变和流动能量接口也没有提供另一条壁面导热执行链。有限热设备使用的 `carrierAccess` 同样没有气体。设计书“气体孔流及气腔壁热交换由气体处理器执行”的后半句没有对应实现。

**直接后果：** 对固定容积、无孔流、无相变的有限气腔施加热壁，即使有明确温差和非零导热物性，气体内能仍没有导热更新路径；加热外壳不能通过壁热交换使其中气体升温增压。热气体对冷壁、以及气体与液体之间的显热交换同样缺失。压力压缩与焓流仍能改变气温，无法补足静止气腔的这条热交换链。

这属于交付功能缺口，不能通过降低温差精度要求解释。它还使排障方向容易偏向 EOS、气腔压力缓存或调度唤醒，实际上缺的是热量交接本身。

**整改方向：** 为集总气腔提供有明确接触面积和接收归属的壁面/液面热交换，与接触载体成对结算同一笔热量。把气腔接收端纳入唯一的热交换职责链，并让调度使用这条链的实际温差；在现有热交换场景中覆盖“热壁—有限气腔—升温增压”的完整过程。

## 13. [P2，代码可确定] 相变动量只看净质量，邻格相反的质量变化会相互抵消

**位置：** `solver/src/main/java/mmm/fluid/CellMacStage.java:334–377`；`CondensedPhaseChangeStage.java:123–135`、`GasLiquidPhaseChangeStage.java:220–236`；`docs/architecture/thermal-state.md:360`。

两个相变阶段把全批次最终液体库存交给 `prepareExternalMomentum`。该方法只知道每个面的旧质量 `M`、新质量 `M'` 和旧速度 `v`，采用 `min(M,M') × v` 更新动量；仅当净质量增大时计算零速混合热，净质量减小时计算移出动能。

MAC 面质量为左右格液体质量之和的一半。相邻两格一边蒸发/冻结，一边凝结/熔化时，真实的移出与加入可以使这个总和完全不变。此时函数保留全部原动量，也不计算该面的移出动能和混合热，丢掉了“旧物质以当前速度退出、新物质以零速加入”的实际过程。

可直接代入代码的反例：左右两格各 62.5 kg 液体，共享面速度 1 m/s；一格移出 1 kg，另一格零速加入 1 kg。面上的旧惯性为 62.5 kg，新惯性仍为 62.5 kg。按当前模型规定，面应移出 0.5 kg 对应的动量，再加入 0.5 kg 零动量物质：

| 量 | 按来源分别交接 | 当前净质量算法 |
|---|---:|---:|
| 面动量 | 62 kg·m/s | 62.5 kg·m/s |
| 面动能 | 30.752 J | 31.25 J |
| 随移出液体处理的动能 | 0.25 J | 0 |
| 零速加入的混合热 | 0.248 J | 0 |

上述是无额外墙面裁剪的内部面代数反例，未冒充完整运行实测。总能量账仍可能闭合，因为本应转热的能量继续保留为动能；规定的相变动量处理却已经被违反。仅有单点蒸发或单点凝结的测试不会覆盖这种抵消。实际移出量和加入量不相等时，也会遗漏其中相互抵消的部分。

**整改方向：** 质量变化计划同时保留各格实际移出量、加入量及输入动量，在面上分别汇总后混合。把这些信息放在共同物质交接契约中，所有相变调用自动继承；用最终库存差反推相变动量无法恢复已经丢失的来源。

## 14. [P2，代码可确定] 相变移出的动能汇总到全域，再按质量分配，能把热量送到不相连的区域

**位置：** `solver/src/main/java/mmm/fluid/CellMacStage.java:335、372、377`；`CondensedPhaseChangeStage.java:130–135`；`GasLiquidPhaseChangeStage.java:231–244`。

`ExternalMomentum` 把所有液体移出的动能压成一个 `double removedKineticEnergy`，不保留来源格。固液相变随后按各格冻结质量分配这个总数；气液相变按各笔新生蒸气的质量分配。两处都在全域批次上执行，没有按实际来源、液路或气腔隔离。

即使没有第 13 项的质量抵消，仅两个互不连通、同一步发生冻结或汽化的区域，也会相互影响转热结果。例如，两处均移出 1 kg，源液体速度分别为 10 m/s 和 0：在未发生额外裁剪的均匀速度区，移出的动能分别为 50 J 和 0 J。当前代码汇总为 50 J 后各分 25 J，静止区域获得了来自另一处的 25 J，运动区域少收 25 J。气液版本会把对应热量交给无连通关系的另一气腔的新生蒸气。

**影响：** 全域内能与总能量断言都可以通过，但局部温度、相变余量和气压取决于同一步另一个区域的速度。只缩小重放区域，或去掉看似无关的远端相变，就会改变问题现场。这是直接增加失败重放和跨文件排障难度的非局部耦合。其根因独立于第 13 项：即便把移出动能总数算对，丢掉来源后仍然分错位置。

**整改方向：** 在共同动量计划中保留移出动能的来源格/库存归属，再由对应相变把它交给该处固相或新生蒸气。复用同一份来源记录处理动量与能量，删除调用方自行按全域质量摊分的两套逻辑。可改造既有相变夹具，使两个断开区域分别运行与同批运行的局部结果一致。

## 第 1 项的影响范围补充：颗粒化学反应也有独立的排水能量遗漏

**位置：** `solver/src/main/java/mmm/fluid/GranularReactionStage.java:810–846`，对照同文件 `420、528–530` 与 `CellMacStage.java:399–411`。

`GranularReactionStage` 在反应候选发布前另行执行 `prepareDisplacement → prepareLiquid → CellMomentumTransport.prepare`，只把动量混合热加进排水库存，随后把运输结果转回普通库存编辑。该链没有调用 `MechanicalEnergySettlement.prepare`，也没有在别处结算被排开的液体格心势能变化。

该阶段确实计算了反应物自身在液体、颗粒和床层间转换的势能差；这些项不包含随后为腾出容量而搬走的其他液体。反应导致向上排水时，仍有额外的液体势能需要支付。此处为代码确定的遗漏路径，本轮未再制作颗粒反应运行夹具，未将第 1 项的 0.5713 J 实测值套用到这里。

**对整改范围的要求：** 仅补 `GranularLiquidDisplacement` 无法完成第 1 项；必须同时迁移颗粒化学候选发布中的容量排水。气腔在内部化学转换中的能量规则需按其自身模型处理，本条明确指出的是被排液体的 PE 遗漏。

## 第三轮对维护目标与稳定性的判断

目前至少存在四种独立的信息断裂：孔流压力预测与实际热量交接采用不同响应；气体在热载体枚举中缺席；相变把加入和移出压成净质量；移出动能把来源压成全域总数。第 1 项又出现另一条复制的排水发布链。它们都需要沿模型、求解阶段、共同提交和验收入口追查，当前整合尚未实现“一处物理规则变动，全部入口自动继承”。

稳定性判断也应收紧到证据范围：第 1 项已经证明系统性增能；第 11 项证明能量守恒条件下仍能产生明显、持续的错误终态；第 8、9 项存在可停滞的控制流；第 12 项使热交换过程根本没有演化。现有成功步、热账闭合和短期机械场景不足以支持“正常耦合场景误差可控”的整体完成判断。

实施方应优先修复能量交接遗漏与孔流热力学闭合，补齐气腔热交换，再把相变的来源质量、动量和能量作为完整计划统一交付。第 13、14 项适合在同一次来源信息重构中处理；逐个调用方追加特判会继续保留这轮审查揭示的维护成本。
